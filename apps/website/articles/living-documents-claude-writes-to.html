Living documents Claude writes to

A note that grows across weeks of unrelated conversations, with every edit arriving as a diff you accept. How the proposal pipeline works and why it exists.

Most AI writing features produce a block of text you paste somewhere. The interesting thing happens when the AI can edit the page itself, over time, from anywhere, and the page keeps being yours. That is a living document, and getting it right is mostly about restraint.

The pattern

You keep a note called "Feature ideas", or "Reading list", or "Things to tell the accountant". Over the following weeks you have conversations with Claude about unrelated things, and now and then you say "add that to my feature ideas". Claude finds the note, reads it, appends a few lines in the same style, and moves on. The note grows on every device you own, in the place you would look for it.

What makes this different from pasting is that nothing is lost in the handoff: Claude sees the existing content before writing, so new entries respect the structure already there; the edit lands as a real change to a real collaborative document, so it merges with whatever you were typing on your phone at the same moment; and you never have to be at the notes app for it to happen.

Why the edits are proposals

The obvious implementation is to let the MCP tool write straight into the page. Selfnote did that first and took it out. A model with a token can rewrite a whole document, and a remote tool call from a chat you are not looking at should not be able to do that silently.

So every body edit that originates from AI, whether it is Claude over MCP or the Assist panel inside the app, becomes a proposal. The server computes the change against the note's current state, stores it alongside a Markdown rendering of the page before and after, and leaves the note untouched. The app shows a badge on the note, you open the diff, and you accept or reject. Accepting applies the change as a normal edit. Rejecting discards it. If the note moved on underneath while a proposal waited, the server recomputes the change against the new state, and if it can no longer be applied cleanly the proposal is marked superseded rather than forced.

Metadata is treated differently on purpose. Moving a note, renaming it, labelling it, or trashing it applies immediately through the MCP, because each of those is one gesture to undo in the app and the diff would add friction for no safety. Body text is where the damage can hide, so body text gets the review.

How a merge works underneath

Every Selfnote note is a Yjs document, a CRDT, which is what lets two people type in the same sentence while one of them is offline. The MCP server sends Markdown, but nothing pastes it: when you accept, the API server reconstructs the Yjs document, applies the change to it, and produces an incremental update that the sync server merges like any client's keystrokes. That is why an accepted proposal appears instantly in every open editor, and why Claude's append and your simultaneous edit never collide.

Save the conversation, then keep it alive

The simplest living document is the one save_conversation creates: a summary of a chat filed as a sub-page under a "Conversations" note, or under any note you name. Over months that parent becomes a searchable log of everything you worked through with Claude, each entry linked back from the place it was about. Later, from a new chat, "what did I conclude about the ingress controller" is a search and a read away.

The save-to-selfnote skill makes the summaries good: a one line overview, the decisions as bullets, the open questions, no transcript. Teaching the model what a good note looks like is most of the work, and it is work you do once.

What keeps it honest

  • Version history. Every note has a timeline of restore points, saved automatically and on demand. A restore is a new forward edit, so even a bad accept is recoverable and nothing is ever destroyed.
  • A record. Every proposal keeps its origin, who resolved it and when, and the before and after text, so you can see afterwards which edits came from the AI and what they changed.
  • The token. One personal access token, revocable in one tap, is the entire authority the MCP server has.
  • Your server. The proposal, the diff and the note never visit anyone else's infrastructure, unless you chose a cloud provider for the model itself.

Try it in one afternoon

Create a note called "Ideas". Connect Claude. In your next unrelated chat, when something is worth keeping, say "append this to my Ideas note". Open the app, read the diff, accept it. Then do it again next week without thinking about it. That is the whole feature, and it is quietly the most useful thing a notebook has learned to do in a long while.
